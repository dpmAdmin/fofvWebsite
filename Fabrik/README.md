# Fabrik

A native iOS and macOS app for AI asset creation, powered by [fal.ai](https://fal.ai).
Generate imagery, enhance and upscale photos, replace skies, virtually stage
empty rooms, and turn stills into cinematic clips — from one SwiftUI app that
runs on iPhone, iPad, and Mac.

> ### Read this first
>
> **This project has never been compiled.** It was written in a Linux container
> with no Swift toolchain, no Xcode, and no Apple SDKs — none of which exist on
> Linux. Every line was written carefully and statically checked (see
> [What was and wasn't verified](#what-was-and-wasnt-verified)), but the first
> real build is yours.
>
> Expect to fix a few compile errors on the first ⌘B. That is normal for code
> written without a compiler, and the structure is sound.

## Getting started

1. Open `Fabrik.xcodeproj` in Xcode 16 or newer.
2. Select your team under **Signing & Capabilities** (the target ships unsigned).
3. Pick a destination — **My Mac**, or an iOS simulator/device — and run.
4. On first launch Fabrik asks for a fal API key. Get one at
   [fal.ai/dashboard/keys](https://fal.ai/dashboard/keys).

### Bundle identifier

The placeholder is `com.fabrik.Fabrik`. Change it to something under a domain
you control before running on a device or distributing. If you do, also update
`service` in `Core/KeychainStore.swift` so the Keychain item matches.

### If the project will not open

The `.xcodeproj` was written by hand rather than generated by Xcode. It uses
Xcode 16's synchronized folder groups, so it needs **Xcode 16+**. If it fails to
open, the recovery is quick:

1. File → New → Project → Multiplatform → App, named `Fabrik`.
2. Delete the generated `ContentView.swift` and `FabrikApp.swift`.
3. Drag the `Fabrik/` source folder in, with "Create groups" selected.
4. In Signing & Capabilities, add **App Sandbox** with *Outgoing Connections*
   and *User Selected File* access — or point `CODE_SIGN_ENTITLEMENTS` at the
   included `Fabrik.entitlements`.
5. Set the deployment targets to iOS 17 / macOS 14.

## Your key, your account

Fabrik ships with **no credentials**. It uses a key you supply, kept in the
system Keychain and sent only to fal. Generations are billed to your own fal
account.

This is why there is no server: an app cannot safely embed a shared API key —
anyone can extract strings from a shipped app bundle — but it can safely hold
*your* key on *your* device.

The trade-off is that everyone who uses Fabrik needs their own fal account. If
you ever need to hand it to someone without one, that is what the web version in
[`../studio`](../studio) is for: it keeps a single key server-side behind a
password.

> **Cost:** every generation is a paid fal call, and video is dramatically more
> expensive than images. Nothing here caps or meters spend — set a budget alert
> in the fal dashboard.

## How it is put together

```
SwiftUI views  ──►  StudioModel  ──►  FalClient  ──►  fal.ai
                         │
                         ├──►  KeychainStore   (the API key)
                         └──►  AssetStore      (library.json)
```

```
Fabrik/
  App/
    FabrikApp.swift      @main, scene setup, macOS Settings scene
    Theme.swift          colours and the shared panel treatment
  Core/
    Catalog.swift        ← the model catalogue. Most edits happen here.
    StudioModel.swift    @Observable state: selection, form, job lifecycle
    FalClient.swift      the fal queue + storage REST protocol
    JSONValue.swift      dynamic JSON, because fal's shapes vary per model
    Asset.swift          library records + output extraction
    AssetStore.swift     JSON persistence in Application Support
    KeychainStore.swift  API key storage
  Views/
    RootView.swift       split-view shell, settings, first-run gate
    SidebarView.swift    catalogue grouped by category
    GenerateView.swift   form + output, side-by-side or stacked
    FieldRow.swift       renders one catalogue field as a control
    ImageField.swift     Photos on iOS, file importer on Mac
    JobPanel.swift       queue position, logs, elapsed time, cancel
    AssetTile.swift      preview, save, re-run, share
    LibraryView.swift    history with per-model filters
    SettingsView.swift / OnboardingView.swift
```

### The fal protocol

There is no official fal SDK for Swift, so `FalClient` speaks the HTTP API
directly. The exact shapes were read out of the official JavaScript client's
source rather than guessed:

| Step | Request |
| --- | --- |
| Auth | `Authorization: Key <key>` |
| Submit | `POST https://queue.fal.run/{endpoint}` → `{request_id, status_url, response_url, cancel_url}` |
| Poll | `GET {status_url}?logs=1` |
| Result | `GET {response_url}` |
| Cancel | `PUT {cancel_url}` |
| Upload | `POST https://rest.fal.ai/storage/upload/initiate?storage_type=fal-cdn-v3` → `PUT {upload_url}` |

Submit returns fully-formed URLs for the follow-up calls, and the client uses
them verbatim instead of rebuilding them — so polling keeps working even if fal
changes its URL layout.

Cancelling the SwiftUI task also sends fal a cancel, so backing out of a running
job does not keep burning credits.

## The model catalogue

Everything Fabrik can do is plain data in
[`Core/Catalog.swift`](Fabrik/Core/Catalog.swift). The sidebar, the input form,
and validation are all generated from it, so adding a model is one entry with no
UI changes:

```swift
FalModel(
    id: "my-model",                      // internal slug, stored with each asset
    endpointId: "fal-ai/some/endpoint",
    title: "My model",
    blurb: "One line on when to reach for this.",
    category: .enhance,
    outputKind: .image,
    eta: "~20s",
    docsURL: URL(string: "https://fal.ai/models/fal-ai/some/endpoint"),
    fields: [
        .sourceImage("The photo to work on."),
        Field(name: "prompt", label: "Prompt", type: .multilineText, isRequired: true),
    ]
)
```

Each `Field.name` is sent to fal **verbatim**, so it must match that model's
documented input schema. Field types: `.text`, `.multilineText`, `.picker`,
`.number`, `.toggle`, `.image`, `.images`. A `.number` field with `minimum`,
`maximum`, and `step` renders as a slider; image fields upload to fal storage
and pass a URL.

### Verify endpoint IDs before relying on them

The catalogue ships with ten models — FLUX for generation, Clarity/AuraSR for
upscaling, Kontext for sky replacement and staging, Kling and Seedance for
image-to-video.

**These endpoint IDs and their input schemas were written without access to
fal's live model gallery, and fal versions models regularly.** Before leaning on
one for real work, open its `docsURL` and confirm the id and field names still
match. A drifted schema shows up as either a validation error naming a field, or
a job that completes with no files — both surface in the app with a link to the
model's fal page.

## The library

Generations are recorded in `library.json` under Application Support: model,
full input payload, output URL, and fal request id. No database, no schema to
migrate.

Only metadata and URLs are stored, never file bytes — which has one consequence
worth knowing: **fal expires stored outputs**, so old entries eventually point
at files that 404. The app shows a placeholder for those. Use **Save** on
anything you want to keep.

**Re-run** loads a past generation's exact inputs back into the form and jumps
to it, so you can change one value and go again.

## What was and wasn't verified

Being precise about this, because it is unusual:

**Verified**

- The fal wire protocol — URLs, methods, headers, and payload shapes were read
  out of the official JS client's source, not recalled from memory.
- `project.pbxproj` structure: balanced, every referenced UUID defined, required
  keys present, and the shared scheme points at the real target.
- All 19 Swift files: balanced delimiters, no duplicate top-level types, no
  unreferenced types.
- The same catalogue and output-extraction logic, in its TypeScript form, was
  exercised end-to-end in a real browser in [`../studio`](../studio) — including
  the "walk the response for anything file-shaped" extractor this app ports.

**Not verified**

- **It has not been compiled.** No Swift toolchain, no Apple SDKs.
- No generation has been run end-to-end against fal from this code.
- No view has ever been rendered, so layout and spacing are unproven.

Known risk areas, in rough order: SwiftUI API details on first compile,
`@Observable` interactions, and the hand-written project file.

## Fabrik on the web

[`../studio`](../studio) is the same catalogue as a Next.js app, verified in a
browser. It keeps one fal key server-side behind a password, so it suits people
who should not need their own fal account. The two share no code — the catalogue
is deliberately duplicated in each language rather than abstracted across them.
